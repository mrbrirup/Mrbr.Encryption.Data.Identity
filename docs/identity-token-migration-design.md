# Protected Identity user-token migration design

Status: complete SQLite and PostgreSQL library workflows and provider-selectable operator console implemented  
Scope: existing plaintext `AspNetUserTokens` rows to the protected UUIDv7 schema  
Target providers: SQLite and PostgreSQL

## Safety position

Migration is never an application-startup side effect and is never triggered by resolving the Identity store. It is an operator-run maintenance process with explicit preflight, backup, read-only enforcement, verification, cutover and cleanup decisions.

The first supported workflow is offline. Token mutation must be disabled for the complete source snapshot, backfill, verification and table-swap interval. An online dual-write migration would require a separately reviewed bridge release and is outside this version.

The process uses a shadow table. It does not overwrite the only plaintext copy and does not encrypt `LoginProvider`, `Name`, or `Value` in place.

## Tables

The existing table remains unchanged during backfill:

`AspNetUserTokens`

- composite primary key: `UserId`, `LoginProvider`, `Name`;
- plaintext `LoginProvider`, `Name`, and nullable `Value`;
- foreign key to `AspNetUsers`.

The executor creates a provider-appropriate shadow table:

`AspNetUserTokens_MrbrProtected_<migration-id>`

- `TokenId`, application-generated UUIDv7 primary key;
- plaintext `UserId` foreign key;
- independently encrypted `LoginProvider`, `Name`, and nullable `Value`;
- fixed-size `RoutingHash` containing the keyed composite HMAC;
- unique temporary index on `RoutingHash`;
- temporary index on `UserId`.

The migration identifier in an object name is formatted without hyphens and contains no secret or protected value. PostgreSQL identifiers must remain within its identifier-length limit; executors may use a documented shortened suffix. All identifiers are generated by the executor and quoted through provider APIs, never accepted as arbitrary SQL input.

## Durable stages

`Mrbr.Encryption.Data.Identity.Migration` defines the stages and validates every transition:

1. `Created` — UUIDv7 manifest created; no database mutation.
2. `PreflightPassed` — maintenance/read-only control, configuration, keys, permissions, free space, backup and source schema verified.
3. `ShadowSchemaCreated` — empty protected shadow table and temporary constraints exist.
4. `BackfillInProgress` — one or more committed batches may exist.
5. `BackfillComplete` — every frozen source row is represented by a written or idempotently verified target row.
6. `VerificationInProgress` — full decrypt-and-compare verification is proceeding in resumable batches.
7. `Verified` — every target row decrypts and ordinally matches all source logical fields, and every recomputed routing HMAC matches.
8. `CutoverComplete` — table names have been swapped, but application writes remain disabled.
9. `RuntimeVerified` — every migrated row has been located and decrypted through the generated application EF/Identity lookup after cutover; writes remain disabled.
10. `PlaintextRemoved` — the operator deliberately removed the retained legacy table after runtime verification, write acceptance, and the retention decision.
11. `RolledBack` — the pre-write table swap was safely reversed; the migration execution is terminal.

Stages cannot be skipped. Backfill counters are monotonic and bounded by the source count captured during preflight. The durable checkpoint contains only the migration UUID, stage, aggregate row counters and the protected-write boundary; it contains no provider, token name, token value, ciphertext, HMAC, key handle, or plaintext cursor.

## Preflight

The executor must fail without schema mutation unless all checks pass:

- the application is in maintenance mode and token mutations are blocked;
- a restorable backup has been created and independently identified by the operator;
- the source table has the expected legacy composite key and plaintext columns;
- no previous unacknowledged migration or shadow table exists;
- the target Identity model and generated source-key map validate;
- `IdentityToken`, `IdentityTokenLookup`, and `IdentityCredential` keys are active and available;
- the routing search-key handle already exists and will remain stable for the whole migration;
- the database account can create, rename and drop the required objects;
- estimated database and transaction-log/WAL capacity is sufficient;
- the frozen source row count is recorded.

Preflight must not generate or replace a key. Configuration fingerprints may be recorded only if they cannot reveal key material, key handles, HMACs or protected data.

## Backfill and resumability

- Read the frozen legacy table in its complete composite-key order using a configured batch size.
- Create each `TokenId` with `Guid.CreateVersion7()` in application code.
- Compute the versioned composite routing HMAC from `UserId`, `LoginProvider`, and `Name`.
- Encrypt provider, name and value independently through the same generated configuration used by the target application.
- Commit the target rows and then durably advance aggregate checkpoint counters.
- Clear avoidable plaintext buffers; never write row values to logs, checkpoints or exception messages.

Restart begins at offset zero and idempotently verifies already-present target routes before continuing. This may rescan work but avoids persisting a sensitive composite-key cursor. Because the source is frozen, offset paging remains stable. A target row with the same routing hash must decrypt and ordinally match all source fields; otherwise the process fails closed as a collision or invalid state.

Known protection and verification failures are returned as result values. Programming errors, cancellation, database connectivity/provider failures and invalid operator arguments remain exceptions. A batch transaction is the retry boundary; no executor may loop indefinitely.

## Verification

Cutover is forbidden until all of the following are true:

- source count, target-ready count and target-verified count are identical;
- every target identifier is UUIDv7 and unique;
- every routing hash is unique and equals a fresh recomputation;
- provider, name and value decrypt and ordinally equal their source values, including null/empty distinctions;
- each `UserId` still resolves to the same user foreign key;
- raw target inspection finds none of the synthetic known plaintext test values;
- the generated runtime store can read representative rows from the shadow model;
- verification is repeated after the final committed backfill batch.

A sample-only check is insufficient. Every row must be verified.

## Cutover and rollback boundary

With application writes still disabled, the executor performs one provider-specific transactional metadata operation:

1. rename `AspNetUserTokens` to a migration-specific legacy name;
2. rename the verified protected shadow table to `AspNetUserTokens`;
3. rename or recreate final indexes where provider naming rules require it;
4. verify the final schema;
5. durably mark `CutoverComplete`.

After cutover, the coordinator reads every retained legacy row in bounded batches and verifies it through the generated runtime EF/Identity lookup. This all-row pass must durably reach `RuntimeVerified`; a sample smoke test is not sufficient. `AcceptProtectedWrites` is rejected before that stage and records the irreversible operational boundary after it. Until write acceptance, a metadata-only table swap back remains safe. Once writes are accepted, the legacy table is stale; swapping it back could lose authentication state and is rejected as `RollbackUnsafe`.

Rollback after protected writes requires a separate reverse data migration or restoration from a coordinated backup. It is not a DDL toggle.

## Plaintext removal

The legacy table remains access-restricted during an explicitly chosen observation period. Removing it is a separate operation that requires the matching migration identifier, `RuntimeVerified`, durable protected-write acceptance, and explicit acknowledgements that backup retention, replicas/exports, and irreversible removal have been addressed. Each provider executor validates the protected schema and provider integrity immediately before deletion. If the table drop commits but checkpoint persistence fails, a retry reconciles the missing legacy table and durably records `PlaintextRemoved` rather than failing on a second drop.

Key retirement is not part of this migration. Source keys and search-key handles used for protected rows must remain available according to the separate key-recovery and re-encryption process.

## Provider requirements

### SQLite

- Use a real file database for migration tests so restart and transaction behaviour are exercised.
- Account for SQLite table-rebuild semantics when replacing primary/foreign-key structures.
- Hold an exclusive maintenance connection during the final swap.
- Run `foreign_key_check` and an integrity check before accepting writes.

### PostgreSQL

- Use native `uuid` for `TokenId`.
- Keep the table rename and final constraint/index changes in one transaction while writes are disabled.
- Use bounded transactions for backfill to limit WAL growth and lock duration.
- Verify constraints and query plans after the swap.
- Do not use `UNLOGGED` tables because crash recovery and replication semantics are part of migration safety.

## Executor acceptance tests

- empty, single-row and multi-batch databases migrate successfully;
- null and empty token values remain distinct;
- restart after every committed batch is idempotent and creates no duplicate route;
- source-count change, HMAC collision, corrupt target ciphertext and missing/retired keys fail closed;
- cancellation rolls back only the active batch and preserves the last durable checkpoint;
- stage skipping and decreasing counters are rejected without exceptions;
- table-swap rollback succeeds before protected writes and is refused afterward;
- SQLite and PostgreSQL final schemas match the clean protected schema;
- logs and checkpoint storage contain no protected values;
- the standard Identity token workflows pass after cutover;
- protected writes cannot be accepted before every retained row passes the generated runtime lookup;
- the legacy table is not removed automatically and incomplete or mismatched approval is rejected;
- retry after plaintext-table drop but before checkpoint persistence records the completed removal.
